TuitionShield AI — Technical Documentation
6. Sandbox Payment Workflow
Project: TuitionShield AI
Competition: 2026 Shenzhen International FinTech Competition — International Track, Topic C
Payment architecture: Simulated payment ledger with explicit user approval
Status: Proposed design — implementation and testing not yet verified.
1. Purpose
The sandbox payment workflow demonstrates how an AI financial agent can prepare and complete a controlled financial task without accessing real banking systems or moving real money.
TuitionShield AI allows a student to request a simulated tuition payment. The system validates the request, presents a payment proposal, waits for explicit user approval, revalidates the proposal, and records the simulated result in a sandbox ledger.
The LLM may help prepare a proposal, but it must never independently authorize or execute a payment.
2. Design principles
1.	No real money movement or bank integration in the MVP.
2.	Every simulated payment must be associated with an authenticated user.
3.	Approval must come from an explicit user interaction.
4.	Approval must be tied to the exact payment details.
5.	Every execution must be validated by trusted backend code.
6.	Duplicate requests must not create duplicate ledger entries.
7.	Failed operations must not be reported as successful.
8.	Every significant state transition must be auditable.
3. Architecture
The payment workflow uses these components:
•	Frontend: Displays proposals, warnings, and approval controls.
•	Backend API: Authenticates requests and enforces business rules.
•	AI agent orchestrator: May request creation of a payment proposal.
•	Payment proposal service: Validates and stores proposals.
•	Approval controller: Records explicit user approval.
•	Sandbox ledger: Stores simulated payment results.
•	Audit service: Records important actions and outcomes.
•	Supabase PostgreSQL: Stores application records and workflow state.
The frontend and LLM are not trusted to enforce payment security.
4. Payment state machine
A payment proposal follows this lifecycle:
stateDiagram-v2
    [*] --> Draft
    Draft --> Validated: Inputs pass validation
    Draft --> Rejected: Invalid request
    Validated --> AwaitingApproval: Display proposal
    AwaitingApproval --> Rejected: User declines
    AwaitingApproval --> Approved: Explicit user approval
    Approved --> Executing: Backend revalidates
    Executing --> Executed: Ledger operation succeeds
    Executing --> Failed: Operation fails
    Approved --> Expired: Proposal expires
    Failed --> Executing: Safe retry
    Executed --> [*]
    Rejected --> [*]
    Expired --> [*]
The backend must enforce allowed transitions. A client must not be allowed to change a proposal's status directly to approved or executed.
5. End-to-end workflow
Step 1 — Request a payment
The user asks the AI agent to prepare a simulated tuition payment.
The agent may propose calling a payment-proposal tool. The backend independently authenticates the user and validates the request.
Step 2 — Validate the payment details
The backend checks:
•	Proposal ownership and authorization.
•	Positive, valid payment amount.
•	Supported currency.
•	Recipient label and payment purpose.
•	Related tuition obligation, if applicable.
•	Configured amount and request limits.
•	Existing proposal or duplicate request references.
Invalid proposals must be rejected with a clear explanation.
Step 3 — Create the proposal
The backend creates a unique proposal ID and records the validated payment details.
The initial status is awaiting_approval after validation succeeds and the proposal is ready for review.
The proposal should include:
•	Proposal ID.
•	Amount and currency.
•	Recipient or payee label.
•	Purpose.
•	Related obligation, if applicable.
•	Creation time and expiry time.
•	Current status.
•	Warnings or limitations.
Creating a proposal does not execute the payment.
Step 4 — Display the approval screen
The frontend displays a clear confirmation screen showing the exact payment details.
The user must be able to approve or decline the proposal. The approval action must be separate from ordinary chat text.
The system must not infer approval from statements generated by the LLM or from the mere creation of a proposal.
Step 5 — Record approval
When the user explicitly approves, the backend verifies:
•	The authenticated user owns the proposal.
•	The proposal is awaiting approval.
•	The proposal has not expired or been rejected.
•	The proposal details still match the details presented for approval.
The backend records an approval reference associated with the specific proposal, the approving user, and the approval timestamp.
If any material payment detail changes, the old approval must no longer authorize execution.
Step 6 — Execute the sandbox operation
The backend revalidates the approved proposal before executing it.
The sandbox ledger records the simulated result. The ledger operation must be protected against concurrent requests and retries that could otherwise create duplicate effects.
If the operation succeeds, the backend records the ledger reference and execution timestamp and changes the proposal status to executed.
If the operation fails, the system must record an appropriate failure status. It must not report success without authoritative confirmation from the ledger operation.
Step 7 — Show the result
The frontend displays:
•	Simulated payment status.
•	Proposal reference.
•	Amount and currency.
•	Execution timestamp, if successful.
•	Sandbox ledger reference.
•	Any error or limitation.
The interface must clearly state that this was a simulated transaction, not a real payment.
6. Database requirements
The implementation may use the previously proposed payment_proposals, financial_transactions, and audit_events tables, together with a dedicated sandbox-ledger table if that provides a clearer separation of responsibilities.
Required safeguards include:
•	Unique proposal identifiers.
•	Ownership enforcement.
•	Validated status transitions.
•	A unique idempotency key for each logical execution.
•	A unique ledger reference to the originating proposal.
•	Appropriate foreign keys and constraints.
•	Atomic or concurrency-safe ledger updates.
•	Append-only audit records for ordinary application users.
A proposal must not be considered executed merely because a transaction record was created in the frontend.
7. Idempotency and duplicate prevention
An execution request must include an idempotency key generated or validated by trusted application code.
The server must guarantee that repeated requests for the same logical execution do not create a second ledger effect.
If a retry occurs after a timeout, the server must determine whether the original operation succeeded before deciding to execute again.
If the operation's status is uncertain, the system must reconcile it using the proposal ID and idempotency key. It must not blindly create another transaction.
8. Error handling
Situation	Required behavior
Invalid amount	Reject the proposal.
Unsupported currency	Reject or request a supported currency.
User is not the owner	Deny access.
User declines	Record rejection; do not execute.
Approval is missing	Block execution.
Proposal has expired	Require a new proposal and approval.
Payment details changed	Invalidate the previous approval.
Duplicate execution request	Return the existing result or reject safely.
Database failure	Do not claim successful execution.
Timeout with uncertain result	Reconcile before retrying.
Ledger operation fails	Record failure and provide a clear status.
LLM API is unavailable	Allow supported non-AI workflow or show a clear error.
9. Execution evidence
For the competition submission, capture a reproducible workflow using fictional student data.
Required evidence should include:
1.	The original payment request.
2.	The created proposal and its unique ID.
3.	The approval screen.
4.	An execution attempt before approval that is rejected.
5.	The explicit approval event.
6.	A successful simulated ledger entry.
7.	The final proposal status.
8.	Audit records connecting the proposal, approval, and execution.
9.	A duplicate-execution test demonstrating that no second ledger effect occurs.
Screenshots and logs must come from the actual implementation. Never fabricate execution evidence.
10. Acceptance criteria
The workflow is ready for demonstration only when:
•	Payment proposals can be created and reviewed.
•	The backend requires explicit approval.
•	Approval is tied to exact proposal details.
•	Unauthorized execution is blocked.
•	Duplicate and concurrent requests cannot produce duplicate ledger entries.
•	Failures do not generate false success messages.
•	The sandbox result can be traced through audit records.
•	The application clearly distinguishes simulated payments from real financial transactions.
Implementation status: Proposed design. Each criterion must be implemented and tested before being marked complete.
