1.1. System Overview
TuitionShield AI is an AI-powered financial co-pilot designed to help international students understand, plan, and manage the financial requirements of studying abroad.
The system combines a conversational AI agent with deterministic financial calculations, structured financial data, risk analysis, and a controlled payment simulation environment.
Unlike a conventional financial chatbot, TuitionShield AI is designed to complete structured financial tasks. For example, when a student asks whether they can afford an upcoming tuition installment, the agent retrieves authorized financial data, invokes the financial calculation engine, evaluates the result, and presents an evidence-based explanation.
If the student asks to prepare a tuition payment, the system validates the obligation, checks the available balance, and creates a simulated payment proposal. The proposal cannot be executed until the student explicitly approves the exact transaction details.
The MVP will not connect to real bank accounts or transfer real money.
Primary objectives
1.	Provide an accurate overview of a student's financial position.
2.	Forecast future cash flow and identify potential funding shortfalls.
3.	Simulate financial scenarios, including changes in expenses, funding, and exchange rates.
4.	Enable controlled execution of simulated financial operations.
5.	Maintain traceable records of financial calculations, approvals, and simulated transactions.

1.2. Architecture Design Principles
The system follows six core principles.
1. Deterministic financial calculations
Financial arithmetic, balance updates, affordability checks, and risk calculations are performed by application code rather than generated by the language model.
2. Controlled AI tool execution
The AI can request approved operations through a predefined tool interface. It cannot directly access the database, execute arbitrary SQL, or modify financial records without server-side validation.
3. Explicit user authorization
Financial actions that change the simulated ledger require approval from the authenticated user. Approval applies to a specific transaction, not to an unrestricted instruction.
4. Data minimization
The language model receives only the financial information required for the current task. Unnecessary personal information and uploaded document contents should not be sent to the model.
5. Explainability and traceability
Financial outputs include the relevant inputs, assumptions, calculation results, and supporting records where available.
6. Fail-safe behavior
Missing information, invalid data, expired approvals, failed API calls, and insufficient funds must result in a clear error or an unexecuted proposal rather than an invented result or unauthorized operation.

1.5. Core Application Modules
A. Financial Dashboard
The dashboard presents the student's financial position using data retrieved from the backend.
Planned capabilities:
•	Available funds.
•	Confirmed and pending scholarship funding.
•	Tuition and living expenses.
•	Upcoming payment deadlines.
•	Projected funding surplus or shortfall.
•	Monthly cash-flow visualization.
•	Recent simulated transactions.
•	Financial risk alerts.
All displayed totals must be derived from the underlying financial records. The interface must not independently invent or hardcode calculated results.
B. Financial Planning Service
This module manages the structured financial data used by the application.
Planned data categories include:
•	Financial accounts and opening balances.
•	Income and funding sources.
•	Tuition obligations and installment schedules.
•	Living expenses and recurring costs.
•	Scholarship awards and their confirmation status.
•	User-provided currency rates and assumptions.
The service validates amounts, dates, currencies, and funding status before saving changes.
Pending scholarships and unconfirmed income are tracked separately from confirmed available funds.
C. AI Agent Orchestrator
The orchestrator coordinates interactions between the user, the LLM, and the application's approved tools.
Its responsibilities are to:
1.	Receive a validated user request.
2.	Retrieve only the authorized context needed for the task.
3.	Ask the LLM to interpret the request and, when appropriate, select an approved tool.
4.	Validate the proposed tool call on the backend.
5.	Execute the authorized operation.
6.	Return the actual tool result to the LLM when further explanation is needed.
7.	Present a response based on the verified result.
The model is not the source of truth for financial balances or transaction status. The database and validated application services provide those facts.
D. Financial Calculation and Forecasting Engine
This service performs deterministic calculations.
Examples include:
Funding gap
Funding gap = Total expected expenses − Total confirmed available funds.
Projected balance
Projected balance at period end = Opening balance + Confirmed inflows − Expected outflows.
Scenario analysis
The engine recalculates the financial projection using modified assumptions, such as a 10% increase in living expenses or a two-month delay in expected scholarship funding.
Calculations must use consistent currency handling, defined time periods, and explicit assumptions. Pending income must not be treated as guaranteed cash.
E. Payment Approval Controller
This module controls simulated payment operations.
Planned workflow:
1.	Identify a valid tuition obligation.
2.	Verify the obligation's amount, currency, and due date.
3.	Check the user's available sandbox balance.
4.	Create a pending payment proposal.
5.	Present the exact payment details to the user.
6.	Record explicit approval of those details.
7.	Revalidate the proposal and balance on the server.
8.	Execute the simulated transaction atomically.
9.	Record the outcome and return the transaction reference.
An approval must be bound to the specific proposal and its transaction details. Changes to the amount, currency, recipient, or other material details require renewed approval.
The ledger must prevent duplicate execution through idempotency controls and must reject expired, unauthorized, or already executed proposals.
F. Audit and Execution Evidence
The audit module records relevant events, including:
•	Financial calculation requests and outcomes.
•	Scenario simulations.
•	Payment proposal creation.
•	User approval or rejection.
•	Simulated transaction execution.
•	Failed or rejected operations.
•	Relevant authorization decisions.
Audit records should contain sufficient metadata to reconstruct an operation without unnecessarily storing passwords, authentication tokens, complete private documents, or sensitive prompts.
The final MVP should demonstrate actual sandbox execution logs and test results rather than screenshots alone.

1.6. Data Flow
Flow 1 — Financial affordability analysis
1.	The student asks, "Can I afford my next tuition payment?"
2.	The frontend sends the request to the secure backend.
3.	The backend verifies the authenticated user's identity.
4.	The agent orchestrator identifies the required financial information.
5.	The approved financial-summary and forecasting tools retrieve authorized records.
6.	The calculation engine evaluates available funds, upcoming obligations, and projected balances.
7.	The orchestrator receives the calculated results.
8.	The LLM helps explain the results in natural language.
9.	The backend returns the response and relevant financial figures to the frontend.
The AI must not state that a payment is affordable when required information is missing or the calculated balance is insufficient.
Flow 2 — Financial scenario simulation
1.	The student selects a scenario, such as increasing rent by 10%.
2.	The backend validates the scenario parameters.
3.	The forecasting engine creates a temporary calculation using the modified assumptions.
4.	The system compares the scenario against the baseline forecast.
5.	The application displays the financial impact and any new shortfalls.
Scenario simulation does not modify the user's actual financial records unless the user separately confirms a change through the financial planning interface.
Flow 3 — Simulated payment execution
1.	The student asks the agent to prepare a tuition payment.
2.	The backend validates the tuition obligation and checks the sandbox balance.
3.	The payment controller creates a pending proposal.
4.	The interface displays the amount, currency, obligation, recipient or payee reference, and simulation status.
5.	The student explicitly approves the displayed proposal.
6.	The backend verifies the approval, proposal status, user permissions, and current balance.
7.	The sandbox ledger executes the operation within an atomic database transaction.
8.	The system records the result and a unique transaction reference.
9.	The application displays the actual execution outcome.
If any validation fails, the operation is rejected and the ledger remains unchanged.

1.7. Security Boundaries
The architecture uses several distinct security boundaries.
Boundary 1 — Browser to backend
The frontend is considered untrusted. All input values, requested operations, and claimed transaction states must be validated on the server.
The frontend cannot be trusted to enforce permissions or approve payments on its own.
Boundary 2 — Backend to LLM provider
The LLM is an external service and must not receive unrestricted database access or privileged credentials.
The backend sends only necessary context and exposes a limited tool registry. Model-generated tool arguments are treated as untrusted input and validated before execution.
API credentials are stored in server-side environment secrets, never embedded in client-side code or committed to the repository.
Boundary 3 — Backend to database
Access to financial records is restricted through authenticated server operations, authorization checks, and PostgreSQL RLS where applicable.
Service-role credentials, if required by a trusted backend component, must never be exposed to the browser. Privileged database access must not bypass application-level authorization checks.
Boundary 4 — Payment approval and execution
The LLM cannot directly approve or execute a payment. The payment controller must independently validate the user's authorization, proposal status, amount, currency, balance, and transaction constraints.
Approval must be associated with the exact proposal and verified by the backend. The execution operation must be idempotent and atomic.
Boundary 5 — External financial systems
The MVP does not connect to real banks, payment processors, or external financial accounts.
All payment execution occurs in an explicitly identified sandbox ledger. Simulated transactions must never be presented as real transfers or real-world payment confirmations.

The final schema, indexes, foreign keys, constraints, and RLS policies will be documented after implementation.

1.9. Failure Handling and Reliability
The system must handle failures without silently producing misleading financial results.
Failure	Required behavior
LLM API unavailable	Use a clearly labelled rule-based demo mode or report the service unavailable
Database unavailable	Do not claim that financial changes were saved
Invalid financial input	Reject the input and explain the validation error
Insufficient balance	Reject the payment proposal or prevent execution
Missing or uncertain data	Explain which information is missing and qualify the forecast
Expired approval	Require a new approval
Duplicate payment request	Prevent duplicate ledger execution
Concurrent balance changes	Revalidate the balance and enforce atomic ledger updates
Unauthorized record access	Reject the request and record the relevant security event
Document extraction uncertainty	Require user verification before using extracted information
The application must distinguish between a proposed transaction, a pending transaction, a successfully executed sandbox transaction, and a failed transaction.

1.11. Architecture Acceptance Criteria
The architecture will be considered implemented and ready for demonstration when:
1.	The application can retrieve and display authorized financial records.
2.	Financial totals and forecasts are calculated by deterministic code.
3.	The AI agent can invoke approved tools through the backend.
4.	Scenario simulations produce reproducible results without changing baseline records.
5.	Payment proposals require explicit user approval.
6.	Approved simulated payments update the sandbox ledger exactly once.
7.	Failed or unauthorized payment attempts cannot alter the ledger.
8.	Relevant operations produce traceable audit records.
9.	Database access restrictions and server-side authorization are tested.
10.	The application operates in a clearly labelled demo mode when the LLM API is unavailable.
Conclusion: TuitionShield AI is designed as a controlled AI financial agent rather than a conventional chatbot. Its architecture separates AI reasoning from financial calculations and transaction authorization, enabling the system to demonstrate useful financial task completion while limiting the risks associated with autonomous financial operations.
